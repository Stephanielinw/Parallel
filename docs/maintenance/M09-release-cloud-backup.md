# Parallel Maintenance M09 · 发布体系与云备份准备

> 原始四阶段路线图的 **M09**，以 M08 已合并并部署的 `main` (`a47eaa0541065c497db8b7611dc83169a0273fb7`) 为起点。
> **“云备份准备”不等于上线云备份。** 本轮不增加用户账号、上传入口、云 API、外部服务、数据同步、自动上传、后台上传或远程保存；更不能把未加密的聊天原文传到第三方。
> M00 的“真实 iPhone 两份备份”仍等待用户自行确认，CI 合成数据不构成真机备份。

## 一、现有发布链路发现的风险

1. Pages 引导脚本 `src/App.tsx` 的 `offline.js` 与 `app.js` URL 长期固定为 `?v=m07-manual-recap-20261123a`；根 HTML 样式长期使用旧 `bilingual-20261119a`。**修改代码并不会使 URL 发生变化**，客户端可能继续复用旧缓存。
2. M06、M08 已建立引擎/前端镜像校验，M08 检查了下载 HTML 与 Pages 实际生成的 JS/CSS 相同，但部署物缺少统一的、可以校对文件 SHA-256 的发布清单。
3. 发布源代码 ZIP 的现有清理逻辑主要排除 DB/data 目录及少量敏感指纹，没有独立的“ZIP 内容不可夹带敏感文件”的发布验收。
4. 浏览器“导出完整存档 JSON”和“只读核验”已经存在；**导出内容未加密**，而且文字、图像均可能非常私密。现阶段可以手工保存到用户可信的位置，但绝不能将其当作可直接后台云上传的密文对象。

## 二、发布体系：内容指纹，而不是手动版本字符串

- `scripts/m09-release-manifest.cjs` 使用当前唯一权威的 `public/parallel/offline.js`、`app.js`、`style.css` 的内容计算 **16 位 SHA-256 release ID**，只作构建标识（不是保密验证或签名）。
- Vite 配置将同一个 ID 自动写入 JS 入口加载地址（`offline.js?v=...`、`app.js?v=...`）与 CSS URL；不改运行时数据库、localStorage key 或应用 API。
- Vite build 完成时自动生成 `dist/parallel/release-manifest.json`，记录固定发行产物的 SHA-256 与字节数（Pages HTML、经典 UI、引擎、CSS、单文件 HTML、源码 ZIP）。**不写入** 用户资料、私密请求、API 密钥、设备标识和真实备份。
- 发布清单可用 `node scripts/m09-release-manifest.cjs --check` 只读复核；文件被替换、后置修改或缓存键不匹配会阻止 GitHub Pages 部署。相同输入清单可重复生成同样字节；不把日期、机器名作为版本 ID。
- `scripts/m09-audit-release.py` 对真实构建 ZIP 做独立检查：所需文件齐全；无路径穿越、软链接、私密目录、数据库、凭据文件和禁止的隐私指纹。
- 不将代码指纹误称为签名。清单和文件如果同时被恶意篡改，单凭清单不能证明发行方真实性；签名/信任根另需独立方案。

**缓存边界**：只有在浏览器拿到最新 Pages HTML/JS 入口后，内容指纹才能使脚本绕开旧的同 URL 缓存；不保证 Safari 立即刷新其已缓存的 HTML，更不能代表数据备份成功。

## 三、云备份：不上传的兼容与隐私前置检查

- `scripts/m09-cloud-backup-preflight.cjs` 只处理传入的**本地合成/已导出**备份字符串，校验 `parallel-portable-backup` 版本 1、核心集合、消息 ID 唯一、照片附件是否齐全、API 凭据为空、生成日志未夹带，最多处理 100 MiB。
- 输出仅包含匿名摘要信息（SHA-256、大小、集合是否存在、图片引用计数与检查状态）；**不会返回** Profile 名、角色、原文、场次 ID 或附件内容，也不修改任何存储。
- 返回字段固定为 `encrypted:false, mayUpload:false`。这不是加密函数、云账户凭据，也不是直接可以上传的包；不为绕过上限静默丢弃照片。
- 现有用户端的 `终端 → 存档备份 → 导出完整存档 JSON` 和 `只读核验两份备份` 继续保留。真实 iPhone 需要用户本人导出两份、到不同的可信位置核验；**没有任何静默备份**。

### 将来真正上线云备份之前，缺一不可的单独验收

1. 用户明确选择云提供方并完成授权；移动端独立可靠的上传/下载/中断恢复策略。云 provider、账户权限和 API 敏感信息不可储存在公开代码或明文备份中。
2. **先在设备上端到端加密，再上传**；应使用标准经过审查的 AEAD（如 AES-GCM）、新鲜随机 nonce 与可验证头部；用户掌握密钥/恢复密语，服务端不得取得解密密钥。明确定义 KDF 参数、密钥丢失后的恢复策略，以及云端泄漏威胁模型；不得用硬编码密码“加密”。
3. 不上传明文备份。包括照片、会话、Profile、历史场次、日记、系统日志、API 密钥、记忆索引和文件名等敏感资料；敏感元数据也须最小化。
4. 存档版本检查、原文完整性与照片校验、增量/覆盖及冲突策略、回滚快照、跨设备帐号隔离；必须避免旧设备悄悄覆盖新设备。
5. 在隔离环境进行多版本和大容量恢复、断网/配额/中断/重复上传以及错误凭据/错误密钥测试；真实 iPhone Safari/PWA 手测及 M00 两份备份必须先通过。
6. 专门的隐私与安全审查通过后，再在独立变更中开放云功能，明确告知用户云服务收集的数据及其删除/导出控制。

## 四、M09 机器验收与回滚

- 所有 M00–M08 自动化回归和移动 WebKit 不降级；
- `node tests/m09-cloud-readiness.test.cjs` 验证隐私排除、真实备份 schema 兼容、重复 ID、缺失照片、无网络调用、原存档不写入；
- `node tests/m09-release-integrity.test.cjs` 验证真实 `dist` 中指纹、完整发行文件 SHA-256、改动后拒绝签发、相同产物构建元数据稳定；
- `python3 scripts/m09-audit-release.py` 对真实源码 ZIP 的内容执行安全门禁，不能只检查仓库里的源文件；
- CI 在所有验证通过之后才发布 Pages；正式 `main` 的 build/deploy 均成功，才能结案。

**无数据迁移**：没有 IndexedDB 主存档切换、旧 localStorage 清理、浏览器跨 origin 同步或 Python SQLite 转换，也没有变动 `parallel-portable-backup` 的数据 schema。紧急回滚 M09 代码时保留 M08 功能与数据；不要删除真实浏览器存储或重建 Python 数据库。

**明确未完成的条件**：未进行真实云加密和云备份实现；用户的真实 iPhone 双份备份、物理 iOS Safari 手测仍未由 CI 证明，不能写作已经通过。
