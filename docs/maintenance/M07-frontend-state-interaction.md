# Parallel Maintenance M07 · 整理前端状态与交互

> 原始路线图的 M07（第三阶段·架构模块化）。本任务以**用户界面局部状态、异步请求生命周期与 Profile 隔离**为边界，不改后台聊天、见面、记忆事实、M04 存储实验，也不重做外观。

## 检查结论

M06 已将 `offline.js` 拆成 14 个构建时源码分区，但 `app.js` 仍约 234 KB、3153 行。当前代码的页面状态高度共享，最危险的交叉路径有两类：

1. **相同原作角色、不同 Profile 的前端缓存**：`draftInputs[characterId]`、`surveillanceMap[characterId]`、`diaryMap[characterId]`、`diarySummaryMap[characterId]` 原来只按角色 ID 索引。即使实际后端数据库按 Profile 隔离，前端仍可能在切换身份后展示旧草稿、旧监控或日记标题。
2. **未取消的异步页面请求**：打开记忆、监控、日记、真实聊天照片时，若用户在网络返回前关闭弹窗、切换角色、切换 Profile 或进入其他标签，原请求可能随后再渲染，重新打开旧弹窗。
3. **重复 Profile 切换逻辑**：顶部快速切换和 Profile 页切换使用两套清理语句，未统一重置 `messages`、`meetings`、`translations`、`lastMemoriesData`、`loadedThreadPair` 等临时 UI 缓存。切换后很容易看见上一身份的旧视图。

## 本次修复

### 1. 每个 Profile–角色对都有自己的 UI key

对短期草稿、监控、日记、日记摘要使用现有的 `typingPair(profileId, characterId)`：`JSON.stringify([profileId,characterId])`，与已经按身份隔离的“对方正在输入”状态规则一致。

图库预览缓存过去也只按 `photo_ref` 保存，如两个身份各自保存了相同引用值就有机会看到另一个身份的本地缩略图。现在同样使用 `JSON.stringify([profileId,characterId,photo_ref])`，不更改原始照片 IndexedDB 或实际存档文件。

`renderedThreadId` 暂保留旧字段名（兼容现有视图与测试），但内部值现在变成 **Profile–角色 pair key**，阻止从一个 Profile 切至另一个相同原作角色时复用旧 DOM 与 textarea 草稿。

> 这些都是浏览器内存里的短期 UI 缓存，**没有改变任何存档 schema**。未经发送的草稿也没有被自动上传至故事历史。

### 2. 统一切换 Profile

`activateProfile(nextId)` 收敛顶部快速切换与 Profile 页切换动作，显式保护并保留前一身份的草稿、清空上一身份的聊天、记忆卡片、生成状态及监控/日记 UI 缓存，并让延迟返回的线程/收件箱请求失效。

保留已发送聊天、见面和记忆中的持久内容；后端仍会按当前 Profile 重新加载。未修改切换所在的 tab 及现有按钮外观。

### 3. 异步弹窗失效令牌

`modalRequestSeq` 在发起新角色弹窗请求、真正打开/关闭弹窗、导航、身份/角色切换时递增。一次读取只在以下条件全部成立时才允许渲染：

- 回复令牌仍是最新一次；
- 当前标签仍是消息页；
- Profile 和 character ID 仍与发起请求时一致。

记忆、监控、日记和实拍聊天照片均采用同一个 guard，连错误 toast 也不会在跨身份旧请求失败时打断当前故事。

切换角色发起 `loadThread` **之前**，就撤销上一角色还没返回的弹窗请求权限；不必等新角色聊天读取成功。返回消息列表时同样使旧弹窗失效。角色备注保存完成后的 UI 更新同样按 Profile/角色检查；全局终端读取按导航版本校验，防止切回发现页后旧终端把页面覆盖。

用于真正的写入（发送消息、删除记录、存档恢复）的后端请求不因前端切换而被偷偷取消；守卫只约束**当前显示什么**。

## 回归验收

- `tests/m07-ui-state-isolation.test.cjs`：纯状态契约验证 Profile A 与 B 可以与同一个 Carlos 各自保留草稿；切换后清除消息、见面、摘要、角色引用、队列状态；旧异步请求不得渲染；新请求优先旧请求。额外检查两个 `app.js` 镜像一致。
- `e2e/m07-ui-state-isolation.spec.ts`：实际 WebKit，使用两个合成 Profile 和同一个 Carlos 交替键入/切换草稿，验证不交叉；人为延迟记忆请求，用户关闭弹窗后让响应返回，确认弹窗不会自己复活。
- 所有 M00–M06 回归、构建和原有 WebKit 套件继续执行，CI 全绿方可合并。
- 测试不访问正式 iPhone 存档或照片库，不执行任何线上清理/迁移。

## M07 没有做的事情

- 不将所有前端文件重写为 React，也不修改页面设计或玩法；大型组件拆分涉及 M08 多版本分叉审计的独立风险，不能和当前状态安全改动混成一个 PR。
- `chatBusy` / `flushBusy` 等全局异步指示器仍可能在某个旧请求完成前短暂锁住新线程。这次先保证跨 Profile 不泄露数据或复活旧弹窗；真正的可取消任务状态与请求生命周期全面封装应独立设计测试，避免误断正在保存的消息。
- 自动生成日记/监控仍是 M05 的事实分类协议：M07 仅修前端缓存；不调整 AI prompt 和记忆权威。
- M04 IndexedDB 增量存储仍未完成正式切换，不能把 M07 视为容量问题解决。
- 尚无物理 iPhone Safari/PWA 真机测试，现有移动尺寸 WebKit 不能替代它。

## 后续维护守则

任何未来涉及 `app.js` 的异步 UI：
1. 请求前捕获 Profile、角色和 UI 生命周期标识；
2. 返回后验证请求是否仍然属于当前用户可见页面；
3. 只在验证后更新当前视图，持久写入的正确性由对应业务层保证；
4. 同一角色的不同 Profile 不共享草稿、日记、监控或记忆视图缓存；
5. M06 的两份 `app.js` 静态镜像仍须同步；任何 PR 不得直接覆盖 M05 事实优先级或 M06 offline 源模块。

**验收结论应限定在本次状态隔离与 UI 请求防回流**，而不是宣称整个前端已低耦合或所有竞态都消失。
