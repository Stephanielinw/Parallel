## 故障原因：一个可复现的午夜反例

在一个**合成**的场景中：用户晚间说“我要去睡觉了”，角色回复“晚安”；在次日凌晨约 00:11，`chat_proactive` 又根据一条旧的“未完话题”主动发来“太阳都升到头顶了”式的叫醒短信。

原有提示词已明确写出本地 00:11／凌晨。问题不是 UTC 转换错误，而是两条彼此独立的漏洞：

1. 浏览器 `/proactive-check` 的 startup/idle 触发门槛只看距离上一条消息多久、队列、全局冷却和未完成话题，没有本地静默时段和用户明确说要睡觉的保护。
2. `produceProactiveMessage` 对模型结果缺乏最后的运行时约束；系统文本警告不能保证 LLM 不把凌晨误写成中午，也不能保证 LLM 等待期间用户没有新互动。

Python 本地服务的同名 API 还存在更宽松的候选筛选；因此 M10 同时给两个运行时添加相同的夜间/睡眠前置规则。

## M10-A 明确行为契约

- **自动消息 23:00–08:00（运行环境本地时间）静默**。影响 `startup` 和 `idle` 两种自动检查；**不禁止用户自己发短信、不限制聊天队列响应，也不阻止用户明确点击的 `manual` 主动消息测试**。浏览器使用设备本地钟点，本地 Python 使用其运行电脑的本地钟点。若服务器与客户端位于不同时区，需要未来独立配置，当前不声称跨时区一致。
- **明确近期睡觉意图优先**：当天白天最近 4 小时内用户亲口表示“准备睡觉／午睡／大睡／晚安”等，后续紧跟的轻松语气气泡（比如“嘿嘿”）不会抹掉这条意思；最后明确说“醒了／不睡了”可以解除这项白天保护。只从当前 Profile × 角色的真实用户**短信**取证，不看其他 Profile，也不把监控推演当睡眠事实。
- **生成后再校验**：模型返回前若对方发了新的消息、两人切入线下见面或解除匹配、或已进入静默时间，丢弃过时的主动消息，不能写入聊天、记忆、事件或自动完成原先的“未解约定”。
- **凌晨显著矛盾内容**：保守识别“太阳已经升到头顶／这都中午了”等典型无上下文的“现在已是白天”断言；模型不能把这种文本作为主动 SMS 落库。它是保护关键场景的启发式过滤，不等于任何 LLM 文本都可被可靠验证；避免机械地拒绝“明天中午吃什么”等未来计划。
- **防止重复模型费用**：明显不符合时间的模型回复被拒绝时记下当前主动检查冷却时间，避免频繁重新付费生成，但不写出该条错误 SMS。
- **未完旧话题不能凌驾用户睡眠**：未解决记忆可以作为日间主动联系线索，不能提升优先级绕过静默；本次并没有删除、重写或降权任何既有记忆记录。
