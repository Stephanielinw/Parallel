## 一、为什么需要功能契约

过去出现的三个真实故障（存档配额、见面后旧短信倒流、结束见面后监控停在原地）共享一个问题：聊天、见面、记忆、监控和日记会读写相关状态，但功能间的优先级与失败处理缺少统一的验收基准。

**维护原则**：已有用户故事优先于架构美观；一次改动若破坏本契约，则不得以“另一个功能修好了”为由发布。AI 的措辞、风格和具体日程可以变化；有无丢失记录、时间顺序、角色隔离、来源可信度、切换权限等结构性行为不可随意变化。

## 三、共享事实优先级（设计约束，不声称现有模块已完全实现）

任何需要引用角色经历的子系统都应区分：

1. **已发生 / 有原文来源（observed）**：角色与玩家已实际发出的消息、已经发生的场景行动、明确确认的当前地点、见面开始和结束。
2. **已明确同意但尚未发生（confirmed future appointment）**：双方确认的计划；可以为未来预留时间，绝不能写作已经完成。
3. **AI 推演的个人日程（projected）**：合理的工作、补给、交通、休息等未来活动；可以更新，不等于观测证据。
4. **缺少证据（unknown）**：地点无法确认或生成失败；应显示“去向待核实”，不能沿用三小时前的状态冒充实时情况。

**冲突时**：真实见面地点 > 已确认最新短信事实 > 生成的旧监控日程。原始消息/场景原文高于可能失败或不完整的总结；总结失败不能删除原文。日记写“已发生”时只能引用可核对的事实；允许角色基于推演写计划、意图或感想，但需保持语气区别。

以上是我们要锁定的跨模块契约，**当前只有监控的部分规则已在相关测试得到验证；日记正确区分推演和事实仍是 C-11 缺口**。不能把这里的目标误写成所有旧版本都已经实现。

## 四、生命周期边界

### A. 发现 → 短信

- 发现卡组应记录每个 Profile 当前批次和位置；普通返回继续上一批而不是自动重新刷四张。
- 匹配与短信的关系按 Profile × 角色隔离；退出、切换角色、后台恢复不能意外发送另一角色的排队回复。
- 手机消息只能输出手机语境的文本/照片气泡；模型推理、旁白工件不能混入正文。
- 引用保存关联 ID；撤回只允许己方消息；最新 AI 一轮重抽不是逐条气泡乱重抽。

### B. 短信 → 见面

- 手机里说“我到了”**不等于**用户确认进入线下见面；用户必须点击明确的见面操作。
- 角色开场先以等待中、正在做某事的画面出现，不能替玩家决定到场、接近、回应或内心。
- 角色当前位置与原作时代要有来源，未知地点不能假装已证实。

### C. 见面 → 归档 → 短信

- 每次见面必须有稳定 meeting ID、原始消息、时间与地点轨迹。续接旧见面沿用原卡片与起始时间。
- 场景重抽只重抽当前幕；失败时原成功回复仍应在。
- 见面完成后，新短信 **不能把见面前的“马上开门”“我在楼下”当作刚刚发生**。
- 小结缺失时，允许引用见面末尾原文以衔接，但不能自行创造未记录的离开、抵达、亲密或失约事件。
- 删除原文时必须同步处理来源引用、过期记忆和相应档案；不得污染其他场次。

### D. 见面 → 监控 → 日记

- 真实见面期间，现场时间/地点改变应覆盖推演的未来日程；结束后只重排**尚未发生**的剩余时段，不倒填此前数小时为真实行动。
- AI 日程失败不能导致场景历史丢失；要可重试但不能因反复打开弹窗无限重复付费请求。
- AI 推演日程与“已确认地点”必须明确区分。**与玩家见过面 ≠ 三小时后还在那个地点。**
- 日记应按角色与日期保留，已有日记不能在每次打开时无理由重写；“监控推演→日记既定事实”的风险列入 C-11 的 M02 专项测试，尚未声称已修好。

### E. 存储 → 恢复

- 手机主存档目前是压缩或未压缩的 `localStorage['parallel-portable-v2']`；照片和日志的来源不同。
- 完整备份保留照片并排除 API 凭据、生成日志；文本备份不包含照片。
- 恢复是 **覆盖** 而非合并，必须在隔离环境测试，不在真实手机上冒险验证。
- 写入配额不足时已有记录可读、可导出；不能偷偷清空旧存档或假称写入成功。
- 正式 IndexedDB 迁移、云备份和加密仍属于后续维护任务，不是 M01 的实现范围。
