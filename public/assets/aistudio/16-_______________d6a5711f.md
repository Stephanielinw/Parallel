## 一、板块功能总述

### 1.1 让角色记得相处，而不把所有文字当现实

记忆系统服务的是连续的人物关系：居民应记得自己与馆长说过什么、曾一起完成什么，以及哪些事情只属于自己。它不是把聊天记录无限塞进每次Prompt，也不是全馆共用的一本无所不知的小说。

玩家可以通过聊天、共同专注、阅读、游戏、外出和真实互动形成经历。下一次交流时，相关角色可以回想这些经历，而不必重复初始介绍。与此同时，角色不知道没经历过、没听说过的私事；即使馆长能在UI查看A的Inner Thought，也不表示B获得了这段心声。

记忆并不天然证明其中陈述的事件为真。馆长说“我昨天去了月球”，可成为“馆长曾这样说”的对话经历；它不能只靠模型认可就成为世界已经确认的月球旅行。人物可能猜测、撒谎、误解或创作故事，系统需要保留其来源和表达性质。

### 1.2 四层概念各自解决什么问题

旧Bible的四层是职责划分，**当前代码并非四个独立数据库**。

| 概念 | 为玩家提供的连续性 | 现有承载方式概况 |
|---|---|---|
| Identity Memory | 这只猫一直是同一个角色，价值观、原作经历、表达与身份稳定 | 原始角色资料、prompt、personality、来源和固定外观等 |
| Relationship Memory | 馆长与居民、居民与居民之间的历史和关系不会每次归零 | affinity、双向residentRelationships、Canonical基线、关系事件等 |
| Episodic Memory | 有意义的相处与经历可以被之后回忆 | episodicMemories、聊天原文、日记、旅记，以及完成收据的读时投影 |
| Current State Memory | 对话延续此刻位置、形态、可用性与正在做的事 | cat兼容字段、Runtime实际活动／位置、Narrative当前绑定、业务快照 |

四层共同回答“我是谁、我与你怎样、我们经历过什么、我现在怎样”。不能拿某一层替代全部其他层，也不能因为Current State含文字就让AI控制真实身体。

### 1.3 记忆与知识是两种问题

经历记录回答“发生过或表达过什么”；Knowledge回答“谁合法知道哪项事实”。同一真实事件可以被某人亲历、被另一人听说，也可以始终不为第三人所知。听说者不必因此成为原事件参与者。

当前Knowledge ledger主要围绕Life Thread factId建立知情边，不是对全部聊天、物品与记忆的统一访问控制数据库。普通episodic记录与Knowledge边并存，必须分别说明，不能宣传成所有隐私都已由一个全局权限器保证。

### 1.4 现有子功能

- 规范化每只居民拥有的事件记忆，校验owner、来源、时间、参与者和重要性。
- 按sourceKey去重，避免同一来源多次写入相同记忆。
- 用关键词、人物、地点、主题、近期性和重要程度选择相关片段。
- 对聊天保留说话者归属；识别当前有效回复版本而不是把所有重抽都当新事实。
- 从Focus、Away、Explore、Reader、Truth或Dare等完成收据投影简短经历。
- 多人请求尽量只取共同参与过的经历；单人请求取所属居民的合法经历。
- 区分公开当前状态、单人私人状态和广义历史上下文包。
- 为Life Thread事实建立观察、听闻、告知等知情关系，并对私密Phone回复冻结可用事实。
- 保留原始聊天、日记、日志、关系和业务收据作为不同来源，而不把它们全部自动合并成真相。

其中写入、检索和权限接线的覆盖不等于每一个用户流程已测试。玩家界面如何浏览、归档、删除和导出，分别由相关章节继续核对。

## 二、板块功能背景设定

### 2.1 居民来到猫舍之前已经有完整人生

**DESIGN-APPROVED：** 居民就是角色本人，不是模仿角色的AI宠物；原作身份、经历、重要关系与责任仍然存在。Identity层因此不是通过玩家好感逐条“训练”出来的人设，也不应被普通一次对话覆盖。

猫舍生活添加的是后来共同经历，而非替换原有历史。熟悉的角色可以保留创伤、矛盾、幽默与不同亲疏；高affinity不代表统一甜宠化。是否知道某段原作事实也要符合采用的连续性，不能把不同作品版本的全知资料自动塞进每个角色心中。

### 2.2 内心是私人视角，不是全馆广播

旧Bible`docs/WORLD_BIBLE.md:71–91`明确：记忆不是公共池；角色只有经历、目睹、被告知或合法公共来源才获得信息。馆长能看到某些Inner Thought是一种产品呈现权限，不是其他居民读心的世界规则。

A的私人心声、馆长对A说的话、A自己的Life Thread动机，不能因为一张共享AI表同时为多只猫写作而自动成为B的知识。该原则已批准，不再列为需要重新决定的选项。

### 2.3 回忆可以有主观性，事实边界仍须清楚

人物对同一经历可以拥有不同感受：有人觉得被冒犯，有人觉得是玩笑。系统可以保存这些主观视角，但必须区分“我感到不舒服”与“另一人有意伤害我”的确定事实。关系变化、身体接触、物品转移及事件完成，仍需要对应业务权威。

游戏、小说、象征解读也能成为真实的交流经历。例如“共同读过这章小说”可以记住，书中世界却不会因此出现在客厅。这样的分层既保留叙事自由，也防止虚构内容污染馆舍事实。

## 三、板块功能理论实现路径

### 3.1 来源先于总结

已有设计要求记忆有来源、owner、参与者、可见范围和获知方式。**PROPOSAL-PENDING的实施细化**是：各业务完成后先生成可信的简短收据；文学段落保留为表达原文，检索时明确标记“说过／读过／游戏中呈现”，不把自由Scene整段提升为已证实事件。

一条理想经历应能追溯到具体聊天版本、真实完成活动、已提交交易或合法披露。只有预定靠近、尚未发送消息、失败的专注或取消的游戏，不应记成已经完成。

### 3.2 写入与保留流程

1. 正式业务确认操作或对话发生，建立稳定事件ID和时间。
2. PROGRAM确定实际角色、渠道和参与范围；AI可建议情绪、主题和摘要，但无权添加参与者或制造已完成事件。
3. 校验候选来源与身份，区分陈述、主观感受和确定事实；不合格候选不能破坏原始记录。
4. 按来源ID去重，保存一次；重抽的不同版本不应重复增加关系或变成多段互相矛盾的经历。
5. 需要归档时先保存完整事务，再清理临时记录，保持可追溯性。

旧记录没有可靠来源时，不可直接当成已验证，也不得本轮擅自删除。应该先评估兼容范围，再由馆长批准任何迁移。

### 3.3 按当前任务读取最小有用集合

人物上下文应优先包含正确身份和当前业务事实，再取相关记忆。独处状态文案不需要读取全量私聊；多人Focus不该把某位居民独有的Phone消息拼进公共提示；普通角色对话不应每次重述所有外貌与背景。

检索选择是确定性辅助，不是对记忆真实性的再次认证。相同关键词、近似名字或出现在participantIds中，只能帮助查找，不能独立证明角色真的在场。

### 3.4 聊天、重抽与状态交接

聊天开始前应读取可靠的此刻状态，随后由真实聊天干预接管活动。当前有效回复可即时用于连续交流；正式提交、被其他业务引用与每日归档，需要稳定版本来源。重抽只能替换尚可修改的表达，不能让已发生的物品交易或第三人亲历跟着反复改写。

聊天结束后应安全交还PROGRAM；旧聊天文字不应无限覆盖新的生活活动，反过来取消旧活动也不应使用户刚收到的有效回复消失。这是第11、12、14章共同负责的契约；本章不以新增一个Status副本代替所有权设计。

### 3.5 知情扩散与公共信息

一个人知道factId，不等于必须向馆长全部解释；他可以保留、婉拒或有角色化表达。真正分享时应记录传递渠道和所披露事实，并限定接收者。公共News只允许展示合法公共投影，不能反向泄露隐藏动机或原始私人线程。

理论上，谁被谈论、谁在场、谁后来被告知，应有不同含义。若现有participantIds混用了这些概念，不能只调整检索词解决，应先明确最小元数据契约，再做兼容修复。这里提出设计方向，不在本轮实施。

### 3.6 近期与长期目标

近期优先保护来源真实性、单人／多人范围和业务收据，不需要再增加付费记忆审稿模型。长期是否支持用户标注错误记忆、控制归档与保留年限、明确分享授权，需产品审阅。它们不是当前已实现的功能，也不能成为偷偷清理玩家数据的理由。

## 四、目前板块功能实现路径

### 4.1 身份与关系资料

`js/meeow-data.js`保存内建身份、原作提示、初始状态和Canonical双向关系。不可变关系基线、群体基线及方向记录在`169–270`，运行关系规范化在`283–352`。人物与关系的更新事务在第4、6章另述；本模块不会自行重写Canon。

`buildCatIdentityBlock`在`meeow-memory.js:552–564`组合姓名、馆、stored prompt、固定猫种／眼色、当前形态和affinity，说明安全馆长与亲密度不同。它不是原作事实的联网查询器，依赖输入资料正确。

### 4.2 居民自有episodic数据

`episodicMemories`属于cat，每项包含id、ownerId、sourceType、sourceKey、eventAt、createdAt、summary、participantIds、tags、importance、emotionalWeight、unresolved、knowledgeMode和可选retrieval元数据。

`normalizeEpisodicMemory`在`127–163`要求owner匹配、合法时间、1–5整数重要性和合法知识模式，summary最多280字符，tags最多8个；参与者只保留USER及已知居民，并加入owner。该检查确认结构与归属，**不解释整段中文是否真的发生**。

`appendEpisodicMemory`在`200–217`规范化已有列表、检查sourceKey重复、生成稳定ID和有界检索元数据后push。模块不直接调用模型或localStorage，持久化依赖页面的保存接线。`getEpisodicMemories`返回规范化副本，读时不把旧记录的检索元数据强行写回。

### 4.3 来源与检索

`retrieveRelevantMemories`在`385–441`按允许sourceType、必需参与者、延续sourceKey、关键词、人物、地点、主题及相关性筛选，再叠加重要性、情绪、未解决与近期分数。中文使用相邻二字片段，英文使用词串，泛化词排除；这不是自然语言语义模型。

默认取4条，文本构造默认2400字符；页面owned／common封装通常3条、1200字符。整个字段装入预算，部分历史条目可能不被选中。没进入Prompt不等于存档已删除。

`buildEpisodicMemoryContext`在`491–519`可以合入当前有效主页对话、只读完成经历投影和公共持物事实；调用者明确关闭某类注入才能排除。`includeConfirmedExperiences`是显式选项，不是所有调用默认读取收据。

### 4.4 当前聊天版本与长短上下文

`getCurrentHomepageReplySource`在`466–478`优先取最新含homepageDraft的非系统回复，校验owner；找不到才从归档homepageInteractions中选最近版本。它返回的是当前对话表达来源，不是实际位置权限。

页面`normalizeHomepageMemoryCandidate/storeHomepageEpisodicMemory`见`index.html:20196–20249`：AI候选必须与交流有词项重叠、相关人物受约束，最终summary改写为“馆长陈述（未核实）……；居民回应（对话文字）……”，而非直接保存模型声称的事实摘要。这一层保留真实对话，同时避免自动认证馆长陈述。

`retainHomepageReplySource/finalizeHomepageReply`见`20251–20302`，在依赖或归档时保留版本来源；非日结且时间／形态符合时可发布草稿presentation，归档只记录而不重播旧物理状态。完整发送／重抽UI生命周期仍待第14章核对，不能仅凭这几函数宣布P6聊天问题全部解决。

广义`buildCatMemoryContext`在`583–617`按profile选近期交互、监控、永久日记、Focus、旅记、奈恩简报和当前有效聊天。`standard/homepage/compact/reader/exploreModule/exploreScene`各有条数／字数。它的默认Current status仍来自cat.status；精简单人构造也默认cat.status／innerVoice，但允许调用者传入实时值。

`buildAmbientResidentContext`在`649–664`只提供公开当前状态、人设和共享关系基线，刻意不含Inner Thought。`buildForegroundLeanResidentContextParts`在`666–700`可提供所属角色私人心声。`buildStatusSyncCatContext`在`707–737`则含短心声和历史摘要，因此不同构造器的权限边界并不相同，必须核对真实调用方，不能因文件名相同就混用。

### 4.5 完成经历的读时投影

`getConfirmedExperienceMemories`在`283–368`不另建一份持久存储，而是读取已完成业务记录：

| 来源 | 当前检查 | 投影的意思 |
|---|---|---|
| Focus | COMPLETED、正时长、参与者包含owner、有任务名与时间 | 与馆长完成指定时长的专注；任务名称不证明其叙述结果 |
| Away | 本猫、completed、有return时间；普通需materialized公开痕迹 | 确已回馆，私密Thread外出不泄露内部目的 |
| Explore | solved、结算complete且operation合法、非legacyComplete、同伴匹配 | 完成一次COC调查游戏，不把游戏真相写成馆舍事实 |
| Reader | 本猫同章2–3条合法、唯一段落批注及时间 | 共同读过章节并留下批注，不复制书中剧情为现实 |
| Truth or Dare | 完成回合收据、稳定操作ID、已呈现合法居民事件 | 参加线上游戏，保存有来源的游戏发言 |

`formatEpisodicMemoryEntry:443–450`对对话、阅读、游戏加入“不是客观事实证明”的提示。读取可证明收据形状符合条件，但不能替代每个业务写入者本身的正确性。

### 4.6 多人共同经历与一个仍需重点核对的边界

页面`buildCommonExperienceMemoryContext`在`index.html:20412–20418`：多人从首位居民的owned检索中，要求记录participantIds包含USER和全体参加者；不是读取每个人的全部私聊。单居民则只取其自身相关经历。

但主页候选写入`20241`会把relatedResidentIds加入participantIds，而`getHomepageGroundedResidentIds:20159–20173`允许当前文本／历史文本提及的同馆居民成为related。**提到B不等于B听见了这段私聊。** 这可能与共同经历过滤语义发生冲突，详见MEM-02静态风险。本轮没有新增泄漏复现，不把它宣布为已发生的玩家事故。

### 4.7 Knowledge ledger及私有事实

`index.html:23703–23954`保存factId到knower的边，fact正文仍在Life Thread。normalize要求事实存在、居民存在、时间和sourceEventId有效，并按fact／知情者去重。`applyKnowledgeClaims`还检查当前事件授权factId、居民集合、来源事件和完整evidence包含关系，并识别观察／听闻／发现等词与有限否定表达。

这是一组确定性证据接线，不是证明所有自然语言因果真实的系统。已接受Scene本身若含虚构内容，字面证据仍可能不可信，须结合上游PROGRAM事件权威。

`canInjectPrivateResidentKnowledge:23849–23854`当前只允许专门的单居民Phone reply、intentionalConversation=true且无其他居民输出；不是所有单人Prompt都自动获得这些fact。事实以K1等请求内别名传递，提示允许角色保留、回避、部分披露，不强迫倾倒秘密。

Phone在`23907–23954`冻结Knowledge和episodic上下文，避免之后记录变化重写已声明的请求版本；具体消息披露与归档事务在第23章继续核对。

### 4.8 当前Scene亲历写入及P6证据限制

`storeSharedSceneEpisodicMemories`在`index.html:20336–20359`把record.content前280字符作为summary，给record参与者写sourceType=shared-scene、knowledgeMode=witnessed。结构与参与ID有检查，但这一步没有将内容重建为纯PROGRAM事实。

馆长前述P6材料报告过公共Scene虚构第三人进入可信记忆的复现；指定P6.0／P6.1／跨功能原始报告目录目前不可访问，本轮不能补造其trace或重宣布实机结果。当前这段接线仍是可核验的静态风险依据。不能把历史报告、当前源代码与本轮夹具PASS混成“所有Scene已安全”或“玩家存档已污染”的结论。

### 6.2 四层角色记忆与事实来源仍须分开（DESIGN-APPROVED / 需统一接线）

1. **Identity**：使用稳定`residentId`、作品及版本对应的Canon与固定人格；跨馆、领养、暂退再回来应仍是同一个角色，同源不同改编版本不得混作一份身份。新经历影响理解和选择，不凭聊天声称改写历史设定。
2. **Relationship**：第06章馆长的`cat.affinity`、猫与猫有向关系、关系业务事件各归其主。角色可以因亲历逐渐形成情感判断；**普通直接聊天不自动增加数值好感度**，也不能把高分机械解释成恋爱或同意。关系叙事和数值结算不能互相冒充。
3. **Episodic**：分别保存亲历活动、合法场景新对白、他人所述、本人心声、共同阅读/游戏、物品/礼物事务和主观回顾。每条都要有来源与可信性质，不能只有一段没有出处的文艺摘要。
4. **Current State**：应从本轮合法Runtime活动、位置、形态、owner及Narrative当前有效版本取得，必要时使用**明确注明旧值/更新时间**的快照；不应拿旧`cat.status`或长期记忆去覆盖此刻脚点、动作、活动或人物可用性。

**Knowledge是“谁有资格知道某事”的独立权限问题，不是第五个可以共享的公共记忆仓库。**馆长在UI读取A的Inner Thought是馆长的产品观察能力，不会使B“听见A的心声”。共享AI请求与个人Memory读档均必须遵守这一条。

### 6.3 每次存储先问：发生、说过、相信、还是被描述过？（DESIGN-APPROVED / `MEM-01` P0）

为避免“防止虚构历史”最终变成“不准小猫真正聊天”的错误修法，统一区分以下来源：

| 内容性质 | 合法记忆例子 | 提交底线 |
|---|---|---|
| PROGRAM验证的世界硬事实 | 该猫真实到达某馆、完成一次Focus、真实给出一件物品、活动成功执行 | 仅由对应业务提交后成为硬事实；AI不得据一句话扣库、传送、实施治疗或登记不存在的第三人 |
| 实际发生场景中的**合法新对白与生活细节** | 当次获得授权的A/B共同交流中，A确实说了某句话，B听见并回应；本人有相容神情 | 必须有合法活动与真实参与/可听见证明、已采纳的有效文字版本以及场景最终提交；**可成为真实日后回忆**，不能一概当装饰并丢弃 |
| 可追溯的说法、主观回忆、传闻或想象 | “馆长昨天去月球了”是馆长说过的话；“我以为我们去过花园”是该猫的记忆/信念 | 记下**谁说/谁想/谁知道**，不把所述命题自动升级为客观已发生事实 |
| 阅读、COC、小说、Fanfic、角色演戏 | 猫确实读过某一章、玩过某一场游戏、讨论了小说情节 | 体验是真实的，作品情节**不是馆舍物理史**；保留作品/游戏语境 |
| 尚未发生或已失败的候选 | 预排社交、生成却被拒绝的Scene草稿、未完成交易、被重抽淘汰且未被任何合法场景消费的回复 | 不得当成已发生事件；可以保留审计来源，但与有效人生经历分开 |

**关键例子：**如果合法共同互动期间，A对B说“我昨天看见馆长给我上药”，B可以真正记得“A这样说过”；没有合法照料收据，就**不能**替馆长补造“昨天确实给A上药”。但如果A/B在真实获准Scene里发生了一段新的对话，之后两只猫就可以分别记住自己说了、听了什么——绝不因为这些话由AI写成，就统统拒绝进入记忆。

现行`storeSharedSceneEpisodicMemories`直接用`record.content`前280字符充作各人的`witnessed`摘要，需要从“整段字符串作为事实”升级为“合法场景ID/版本/参与者/可知范围 + 可追溯的已生效叙事片段 + 命题可信类型”。不要求PROGRAM独立理解全部文学语义；只要求它不放弃已知事实边界、未见证者不被赠予经历、未经授权的硬世界动作不通过文字获得权威。旧记录不可未经审核直接清洗或抹除。

### 6.4 统一事件来源与最小元数据契约（IMPLEMENTATION-PROPOSAL / 不擅自改存档）

各业务写入与检索至少需要能表达：稳定`memoryId`、`ownerResidentId`、`sourceType`、`sourceEventId/sourceKey`、`sourceVersion`（含第14章聊天`turnId/replyVersion`）、真实`occurredAt`与记录`createdAt`、实际授权地点/活动、`actorIds`、`witnessIds`、`heardByIds`、`mentionedResidentIds`、`knowerIds`/获知渠道、访问范围、陈述/主观/证实类型、原文引用位置、摘要、主题、重要度、后续纠正/矛盾关联与可用状态。

这是**语义字段清单，不是已经批准具体JSON Schema，也不是让开发者在所有旧行上强制一次性补齐**。现有`participantIds`在不同来源可能混有实际参加者与“对话里提到谁”，必须逐来源拆开：**被提到≠在场≠听见≠知情≠亲历**。`MEM-02`在消除这一混淆前不能标PASS；普通A/B共同记忆检索不得把馆长单独对A谈及B的私聊交给B。

任何旧档、迁移或索引都不可用“存了B的名字”作为把私人事件公示给B的理由。缺乏明确授权字段的历史记录，应采用**保守可见/可信降级、兼容只读与额外审计标识**，不默认推定被提及者都在场，也不静默删除；永久迁移和批量清理需另行核实后明确审批。

### 6.5 真正的AI自主记忆搜索：程序守权限，角色决定什么时候查（DESIGN-APPROVED / CURRENT-MISSING）

馆长特别要求的不是“每次只挑3条给AI、让AI假装一生都记得”，而是一个**能按需主动探索自己记忆库**的体验。推荐交互契约如下：

1. **先决定要不要回想**：当前合法任务/话题触发时，AI可以提出明确搜索意图，比如“查与Odysseus上次在餐厅聊天有关的经历”“查馆长刚纠正的那句话”“查今天晒太阳次数”。这不意味着每条Status都要发起独立昂贵请求。
2. **PROGRAM接收结构化查询**：以请求时刻的居民身份、合法知情权限和用户当前业务范围，执行本地搜索；可以按关键词/别名、语义标签、涉及角色、时间范围、馆舍、来源类别、纠正关联等过滤。**搜索条件由AI提出不等于授权通过**。
3. **先返回少量索引卡**：包含可解释的时间、来源性质、简短摘要、原记录ID及可信标记；这步优先本地处理，不把整个人生史塞进Prompt。
4. **必要时按ID二次阅读**：AI可以从授权结果选取需要的片段，读取对应对话/活动的**原始上下文或有来源的日摘要**，而非只能得到280字截断的孤立结论。阅读时再次验证owner、知识边、来源事件、版本以及当时知道的信息。
5. **有预算、有终点**：每次互动硬限搜索轮数、候选数、读取字符/Token及失败兜底；不能无声调用无限次模型，更不能向其他猫扩大搜索范围。超出预算时说明信息不充分，可以模糊回想或询问馆长，**不要编造命中内容**。
6. **继续原任务**：AI把找到的经历当作证据/人物视角再写回复、Inner Thought或个人生活倾向；不能拿检索结果直接修改物理现实或别猫的秘密。

**成本分层：**索引过滤/排序/去重是本地计算，不需额外模型调用；已在执行的模型请求可低成本提出检索计划。若确实需要“AI阅读搜索结果后再继续推理”，额外一轮模型交互**可能消耗Token**，不应谎称完全免费或无限自主。初版可做“单次提出检索请求→本地返回有限证据→续写”的受限闭环；支持局部多次展开是目标，具体接口、数据库与预算数字需先基准测试再定，不强制购买向量服务/外部记忆API。

**随时可查≠全知或永不出错**：没有搜到历史不代表绝对没发生；本人忘记当下线索也不等于底层档案被删除。对话、公共Narrative、本人独处、群体Focus、Phone需按各自知情边界请求不同范围，不能共享一个“全馆统搜”通道。

### 6.6 保存原始历史与可搜索索引，而非每次塞满Prompt（DESIGN-APPROVED / 保存缺口）

- **原始层**：有来源的实际活动与日内完成记录、原始有效对话及版本链、Scene已接纳内容、Reader/游戏/Focus/Away凭证、私人心声（仅本人可见的知识范围）、业务结果与更正链保留为可追溯历史。是“能恢复证据”的档案，而不是另建一份会漂移的世界真相。
- **搜索层**：可以用本地倒排索引、时间/参与者/来源索引和可重建的摘要/关键词缓存；允许重建**派生索引**，不能因此删除唯一的原始事件。较高级语义检索可分阶段探索，不是上线首要前提。
- **上下文层**：Prompt每次只获得眼前任务真正需要的若干候选/摘要/原文片段，**预算不等于记忆保留期限**。旧检索默认4条/2400字、部分3条/1200字与Narrative的2条/900字是当前不同入口的现状，不是角色一生最多4条记忆的设计承诺。
- **存储与备份层**：不能把“日结删除近期环形队列”和“永久档案也已写入”混为一谈。须明确哪些原始内容只在主档、哪些在IDB/独立索引、哪些实际进入第26/36/37章导出与恢复；原稿已提醒部分正文IDB不在主档导出，**导出漏存档也是长期记忆丢失风险**。写入/归档应具可校验提交、稳定去重及失败恢复，不采用静默过期清理。

不强制所有原始Status刷新都自动成为长期“事实”：**必须先证明生活事件/状态确实生效和属于谁**，才能据它生成个人可回忆记录。未实际发生的20分钟预排或被后发事务覆盖的AI草稿不能冒充日记。对于真正提交的普通生活，不能只因为它“不重要”就禁止归档。

### 6.7 一天晒很多次太阳：日常记录、每日归纳与重要经历（DESIGN-APPROVED / CURRENT-MISSING）

馆长已明确选择**B：完整经历保留＋自然日常归纳＋重要记忆长期强化**，并特别强调“小猫应该记得‘我今天晒了很多次太阳’”。不能把B误解为“只保存大事件，其余自动遗忘”。

**示例（假设已经真实执行且有来源；不是声称真实玩家存档发生过）：**

- 10:20 Telemachus在合法有阳光的地方晒太阳；12:40再次晒太阳；15:00又晒了一次；17:20与Odysseus进行了真正成立的交流。
- **原始经历**：可按发生时刻找到三次已完成的晒太阳活动与傍晚那次实际对话；不因合并而丢掉时间/来源。
- **当天的生活概括**：根据这些记录得出“我今天晒了好几次太阳，傍晚还和父亲说了会儿话”。AI可用符合本人语气的表达，但数量、人物与事件**不能超出来源**。
- **较有分量的经历**：假如谈话里出现真正发生、对本人有影响的新内容，这段记忆可得到较高重要性/未解议题权重；但不意味着早上的普通活动从可检索历史中消失。

**实现边界：**在当地游戏日期切换、下一次有效启动或合法归档节点，程序按该猫当日**已确认的**活动收据/对话/场景提取聚合事实（次数、总时长如确有数据、时段、合法地点、共同参与者）；AI可以负责温柔自然地概括体验和感受，并保留摘要→各原始`sourceId`的引用。若一天记录不完整，不应伪装“从早到晚都在晒太阳”。跨日时区/时间边界一致、补写/重抽后去重可重算；已有摘要被更正时应能更新索引或保留修订版本。

**日摘要不是一段万能事实**：它是原始来源支持下的压缩入口，有准确范围与缺漏说明。猫即使没有经历“改变人生的大事”，也能回忆平凡的一天；搜索“昨天做了什么”应能找到日摘要，搜索“下午那次”还可按ID展开原始片段。

### 6.8 从几天日常到几周的生活习惯（DESIGN-APPROVED / 与第10章接线）

如果某只猫多天持续选择晒太阳，它可以根据**足够多天的真实样本**产生“我最近很喜欢有阳光的地方”的后天认识，进而在合法条件下稍微偏向阳光充足的位置、谈及最近的习惯。相反，偶然一次特殊心情并不能把性格永久改为“爱晒太阳”。

建议将`observablePattern`（程序对实际行动的统计）与`selfBelief`（小猫自己如何解释这些经历）分离。后者可有误解和个性，但由前者、合法主观体验或明确可信交流提供依据。影响生活选择的权重与衰减、角色本来就有的偏好、地点可行性、当天心情和其他业务优先级由第10/11章共同处理；**不新增脱离PROGRAM安排的随意AI身体控制**。

原作Canon、人物基本人格、亲密关系双向业务仍保持边界。后天习惯可以改变、减弱或被新体验纠正；不能凭一段漂亮的日记自动改`cat.affinity`、移动Foot，或让另一只猫无缘无故知道本人私密习惯。

### 6.9 馆长通过普通聊天纠正记忆（DESIGN-APPROVED / CURRENT-MISSING）

**明确产品交互：**馆长无需打开「记忆管理员」或填写错误记录表。在和小猫正常聊天时，直接说“**不，我们没有过。**”“你记错了，上次是在餐厅吧？”或其他自然澄清，小猫应该能理解这是**对自己刚提到或检索出的旧认知提出异议**，自然地回应，并把这次澄清留给将来的自己。

建议链路：

1. 识别本次用户是在反驳**哪一条可追溯的说法**，关联之前的聊天回合/记忆`sourceId`；如果对象不清楚，小猫先用自然语言澄清，不要随机改掉相似的别条经历。
2. 通过合法本人搜索找到原记忆和其证据：是AI没来源地叙述的过去、本人主观猜测、馆长曾说的话，还是有真实完成收据的世界事件。
3. 把**馆长此刻确实否认/补充了什么**作为新对话事实保存，并建立`clarifies/disputes/supersedes-interpretation`等可追踪关联；小猫可以自然承认、困惑或表达自己当时为何那样想。
4. 原始文字和真正发生过的业务事实不被覆盖；对无可靠凭据或被澄清推翻的“确信命题”，降低/撤销其**可信断言地位**。有真实完成收据的硬事实不会因为一句否认就被抹除，但可记录双方存在分歧并进一步核对。
5. 今后任何搜索命中旧说法时，**必须连带带出它的最新纠正/争议链及当前可信状态**；不能只取旧摘要一句，让猫下个月又重复“我记得你给我上过药”的谬误。

**纠正是认知更新，不是历史重写。**在私人对A的聊天里纠正A，不会令未被告知的B瞬间同步。小猫可以有角色化的反应，但不能以“我性格倔强”为借口把来源不足的明确错误永远重新当作客观事实。即使暂时缺少可靠记忆检索，也应保护当前谈话中已形成的纠正记录，避免进入仅本次生效的聊天泡沫。

### 6.10 小猫主动发现矛盾、求证与重新理解（DESIGN-APPROVED / CURRENT-MISSING）

馆长明确希望小猫**没有被提醒时也能发现矛盾**；这不要求全知或全天候后台独立思考。可以把轻量检查嵌入发生新经历、完成日摘要、触发相关检索、出现来源版本变化或正常AI写作的适当时机。

**可实施的分层：**

1. **程序发现结构性候选**：相同事件ID或高度关联人物/日期/地点出现互不兼容的陈述；相同来源的新旧解释发生变化；用户明确否认过的说法又被检索到。只标记“**可能冲突**”，不自动判谁对。
2. **小猫按需查证**：AI仅阅读有权访问的少量相关原始记录及纠正链，尝试区分记忆混淆、观察角度、听来的故事、时间演变或真正互斥的主张。对涉及别猫的秘密，只能依据本人合法所知进行推理。
3. **形成可修改的认识**：例如“我以前以为是在花园，但能查到的记录显示那天是在餐厅；也许我弄混了两次见面”。这可以成为本人私有的`belief revision`/疑问或反思，关联证据和置信程度，不改变原始活动坐标。
4. **遇到证据不足则保留疑问**：日常记录缺漏、个人叙述互异、兴趣随时间变化都不能机械判断为“有人撒谎”。没有证据不能擅自宣布某猫从未做过某事。
5. **反思可随新证据再次更新**：未来再查到更完整的聊天或活动记录，能够修正刚才的推论；未经公开表达或告知的私人反思不自动成为他猫知识。

**重要区别：**“过去不喜欢甜食，现在喜欢”可能是时间变化而非矛盾；“A觉得被冒犯，B觉得只是玩笑”也可以同时真实。程序硬事实用于约束事件发生；AI擅长解释主观语境，但不能保证每次语义判断正确，不可把它的反思当成唯一权威数据库。

### 6.11 知情权必须跟随具体信息，不跟随搜索请求扩散（DESIGN-APPROVED / `MEM-02/06` P0）

- **本人私有**：该猫自己的Inner Thought、未公开打算及生活理解，可在本人合法请求中调用；共享Narrative可以为个人内心写作使用本人私有背景，但不得因此写出别人实际听见。
- **馆长对A单聊**：可以成为馆长与A的真实交流；提及B、给B取昵称或说出B名字均不赋予B进入原对话的权限。
- **公开共同经历**：PROGRAM核准谁真正参加、在何处、何时能听见哪部分；合法的现场对白可构成参与者各自的经历，不需要假定所有目击者听到全部内容。
- **二手传达**：B通过A转述知道一条说法，B记住的是“A向我说过X”；不能自动登记B亲历了X，也不能把X自动判定为事实。
- **私人Life Thread/Phone**：现行Knowledge ledger为部分`factId`建立边；未来若统一到更多渠道，必须在读取/写入时都检查合法`knower`、来源与披露范围，而不是把所有有名词匹配的资料都开放。
- **群体搜索**：多个居民出现在同一Prompt时，不能合并成超集后把A独有的秘密写成B的发言。需要个人写作上下文的，按角色隔离注入或显式分组；公共段只用合法共享事实。

`MEM-02`的`relatedResidentIds → participantIds`必须从写入入口修复并以**馆长私聊A提及B→A/B共享Scene→抓取Prompt**做反例；`MEM-06`的文字证据门禁不能仅通过加入更多正则关键词来宣告自然语言隐私语义完全安全。语义不确定时降低事实声明/保留来源，而不是扩大授权。

### 6.12 聊天重抽、纠正版本、历史日结必须一致（DESIGN-APPROVED / `MEM-05` P1）

遵守第十四章已批准的**重开聊天也可重抽最后一轮**：仅对同一只猫，在该猫尚未收到馆长下一条Direct消息、且不存在不可逆现实后果时，跨页面/跨日仍可重新生成回复；**不设纯时间超时**。历史重抽必须以原回合有权访问的时间快照为上下文，不读入后来才知道的秘密或把现时Foot写回过去。

- 原始馆长输入只有一份，回复版本用`turnId/replyVersion`稳定标记；当前有效回复、被引用旧版本和已提交事实不得混为一谈。
- 被Phone、已完成群体对话、交易或他猫记忆真正消费过的旧版本仍应保持可追踪；不准靠重新抽取一个更温柔回答逆向消除已发生事件。
- 已生效历史的新对白允许进入角色经历，但**仅按真正发生/有权得知的版本与内容记录**，不把一回合多次候选记成数次会面。
- 被更正过的旧说法，未来在历史重抽/日摘要重建时仍必须看见有效纠正链；重抽某一段展示表达不等于删除真实发生的下一段馆长纠正。
- 日结与第37章快照需区分“当前世界状态”和“某回合显示过什么”。不能因归档已冻结就错误宣告该猫的最后一轮重抽权失效，也不能日结无限重播某条旧Status覆盖实际正在做的事。

与第11章owner持续持有/同窗返还，以及第12/14章Status和Inner Thought最新展示复核为**共享验收**。不在第16章凭记忆结构变更宣称聊天前快照、CHAT-02滞后一轮或生活交还已经修好。

### 6.13 长期保存、规模、缓存与导出：不能偷偷用“遗忘”解决容量（DESIGN-APPROVED / `MEM-07/08`）

**已批准的方向**是保留确实发生的历史并提供可检索归纳，而非设置“超过30天自动忘记”“只留前100件大事”“每天重写一份不可追溯的日记”等未经批准的产品规则。普通小事可以低优先召回，但**低优先不等于到期删除**。记忆本身也不应随着一只猫暂退馆舍而无来源归零。

推荐工程验收：

1. **增长测试**：模拟少量和大量居民、多年逐日事件，度量本地写入时间、索引增量、查找延迟、主档/IDB容量、Prompt长度、反思触发次数与实际成本。可估算后再设可调预算，不随意写死没测过的数量。
2. **存储层区分**：原始内容、来源收据、引用链、日摘要、检索派生索引、短时缓存须各有保留和备份契约；派生索引坏掉可重建，原始历史不能只存在易过期临时缓存。
3. **事务与恢复**：保存中断、刷新、旧档导入、主档存储不足、IDB不可用时，应有明确失败与可恢复策略，保证不会界面宣称“记住了”却无声永久遗失。关联更正、重抽和日摘要必须避免部分写入造成相互矛盾。
4. **备份导出**：第26/36章要验收**实际恢复出的聊天正文/原始档案**，不能只检查主JSON里有episodic摘要；原稿指出某些IDB正文未进入主档导出，应保留此缺口，不能假称已有完整备份。
5. **隐私与权限测试**：任何索引、查询结果预览、日志或错误提示都不应绕过用户数据/居民知识的原始权限；删除派生缓存、重建索引与归档读取都需通过非参与者隔离。

是否未来增加用户可选清理、导出细粒度、空间上限或离线存储迁移，是可讨论的工程/产品扩展；**本轮不批准无提示自动遗忘或任意改写用户旧档**。

### 6.15 给Codex的优先实施顺序（产品目标已定，技术选择待测）

**第一阶段：保护来源与访问权（优先P0）**。先区分participant/mentioned/witness/knower，防止Scene正文未经事实审核变成硬历史；保留本来合法的新对白入记忆。补跨权限读写反例与旧档兼容保护，避免把修P0变成“什么都不能记”。

**第二阶段：可靠事件与日常档案**。打通本人实际完成的生活活动、有效聊天、共同场景、原始消息版本、日结与长期归档；实现从有来源记录生成每日自然概括和按源查看，保证普通日常可记、可回溯。处理存档提交、IDB/主档恢复与增长测试。
